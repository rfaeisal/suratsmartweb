Sip, usulan valid dan cukup ringan — kami tambahkan sebelum strict
enforcement diumumkan.

Yang berubah di GET /api/v1/rosters/today:
- +already_checked_in  (bool, required)
- +already_checked_out (bool, required)
- +checked_in_at       (ISO8601 UTC, nullable — recordedAt tap MASUK
                        pertama yang VALID hari itu)
- +checked_out_at      (ISO8601 UTC, nullable — recordedAt tap PULANG
                        pertama yang VALID)

Semantik penting:
- can_check_in / can_check_out TETAP hanya cek window (tidak
  memperhitungkan sudah absen atau belum) → mobile combine sendiri:
  can_check_in && !already_checked_in.
- Hanya event MASUK/PULANG yang dihitung. Event LEMBUR_MASUK/LEMBUR_PULANG
  TIDAK di-count (biar chip lembur bisa dibedakan kalau nanti mau
  dibedakan; kalau butuh timestamp lembur, ambil dari /attendance/me).
- Filter status = VALID → kalau admin mark attendance INVALID, chip balik
  ke "Bisa sekarang" dan pegawai bisa absen ulang.

Soal bonus error code ALREADY_CHECKED_IN/OUT di POST /attendance:
Untuk sekarang kami SKIP dulu — backend tidak memblokir double tap.
Alasannya perlu konfirmasi ke bagian kepegawaian apakah pernah butuh
multiple entries (misal skenario koreksi absen manual). Kalau mereka
setuju strict, kami tambahkan di iterasi berikutnya. Chip di card sudah
cukup mencegah kasus normal, jadi selaras dengan yang kalian bilang.
